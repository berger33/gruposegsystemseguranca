## Ordem de implementação para uma demonstração local honesta

1. **Definir escopo de aceite e segurança (P0).** Confirmar quais dos 222 IDs obrigatórios entram na aprovação inicial; marcar os 6 condicionais explicitamente. Corrigir `SEC-04/05/06/07/13..15`, handlers client-security incompatíveis e matriz de autorização antes de ligar 82 componentes à UI. Critério: TI/RH/Marcelo/colaborador/cliente têm sessões individuais e rotas permitidas/negadas com teste HTTP por recurso, incluindo revogação.
2. **Base local durável (P0).** Criar instalador/atualizador Windows com PostgreSQL 17, dados e arquivos privados em diretório exclusivo **persistente fora do ZIP**, migrations com checksums, secrets locais gerados e guardados no SO, rotina de início/parada, recuperação de falha. Separar completamente QA descartável do ambiente de demonstração persistente. Critério: reiniciar PC/servidor e verificar que dados sintéticos, documentos e contas permanecem; backup/restore de cópia isolada com evidência e sem perda. Nada de dados reais antes de segurança/backup/privacidade.
3. **Entrega vertical por papéis (P1).** Ligar só os componentes revisados à navegação protegida e completar jornadas: público/leads → CRM/proposta → contrato → implantação/operação; RH/colaborador; cliente; financeiro/gestão; TI. Para cada lote: formulário, regra/validadores, API, escopo, persistência, histórico, erro/vazio, E2E e UAT. Critério: o usuário completa tarefas fictícias e vê os mesmos dados após reiniciar; não contar cartões descritivos.
4. **SMTP adiado sem fingir sucesso (P1).** Manter SMTP **desligado na aplicação local**, sem envio externo. Ensaios automatizados podem usar captura efêmera de mensagens separada da instalação do cliente. Na demonstração, entregar convites manualmente somente por canal restrito e auditado quando seguro; deixar recuperação de senha indisponível enquanto não houver canal de verificação seguro. Nunca enviar mensagem real nem apresentar e-mail como “enviado”.
5. **Todas as integrações: inventariar dependência e solução por ID (P1).** WhatsApp/API, fiscal (NF-e ou NFS-e conforme atividade), gateway, eSocial/relógio, CFTV/biometria, calendário e storage remoto podem exigir fornecedor, dispositivo, contrato ou parecer; a IA local exige hardware/modelo/base aprovados. **Não dispensar nada tacitamente.** Para cada requisito afetado, apresentar ao proprietário: (a) integração real com credenciais/provedor/equipamento fornecido e autorizado; (b) alternativa local funcional e equivalente se existir, testável; (c) impossibilidade atual e proposta explícita de mudança de escopo/ordem, dependente de aceite. Simulação não satisfaz os 222 IDs.
6. **Acesso remoto protegido ao PC (P0 antes de entregar link).** Depois de endurecer o aplicativo, manter Node e PostgreSQL no PC (PostgreSQL acessível só localmente) e expor **apenas o aplicativo** por HTTPS através de túnel reverso autorizado. Preferência: domínio próprio no Cloudflare + Cloudflare Tunnel/Access, com login do próprio sistema também. Alternativa para testar sem domínio: Tailscale Funnel + autenticação do sistema (o endpoint do Funnel é público, não restringe usuários por si). O cliente recebe um link HTTPS e uma conta individual, sem instalar GitHub ou software de desenvolvimento. Testar com dispositivo fora da rede local; configurar disponibilidade, reinício, URL pública/cookies/origem, logs, rate limit, controle de acesso e procedimento para desligar o link. Não iniciar túnel, abrir porta, criar conta externa ou expor base antes da autorização explícita.
7. **Gate de entrega local/UAT (P0).** Executar CI e E2E Windows + PG persistente; permissões/tenants, restauração, navegadores/acessibilidade, cenários de erro e aceite formal de cada módulo/ID. Entregar manual de instalação/suporte, status honesto do SMTP desativado, pendências externas autorizadas e versão imutável do pacote. Só depois planejar migração de dados/segredos para hospedagem com aprovação separada.

## Link e limites: três rotas concretas

| Opção | O cliente faz | Condições / limitação |
|---|---|---|
| **A — Recomendada para acesso autônomo:** domínio próprio + Cloudflare Tunnel e Access | Abre `https://sistema.seudominio...`, autentica-se no controle de acesso e na conta individual do sistema. | Exige domínio sob controle no Cloudflare e configuração/autorização do serviço; túnel só encaminha ao PC, não hospeda aplicação/banco. HTTPS, proteção de origem e teste externo obrigatórios. |
| **B — Sem domínio próprio:** Tailscale Funnel | Abre link HTTPS `*.ts.net`, faz login **no sistema**. | Exige conta/configuração Tailscale no PC; **endereço publicamente alcançável por qualquer pessoa** (o login da aplicação deve proteger os dados), limites de largura de banda e PC ligado. Não expor antes de auditar segurança. |
| **C — Sem acesso remoto direto:** compartilhamento de tela | Clica no convite de reunião e vê o sistema junto com o proprietário. | Útil para demonstração imediata sintética, mas **não** permite avaliação autônoma em horário livre. |

**Decisão do proprietário:** opção **B (Tailscale Funnel, sem domínio próprio)** escolhida para o acesso posterior do cliente. Preparar o aplicativo para essa rota, mas **não criar conta externa nem ativar o Funnel até passar os gates de autenticação, segurança, persistência e teste de acesso externo, e obter autorização específica para expor o PC**. O cliente abrirá o link no navegador, sem instalar Tailscale; ainda precisará entrar com sua conta individual do aplicativo.

GitHub Pages/README/release **não executam** o servidor Node nem o PostgreSQL do PC: um link GitHub seria apenas para baixar código/ZIP, contrário ao pedido de “clicar e usar”. O ZIP QA atual apaga os dados ao parar. `127.0.0.1` é visível só no próprio PC. Um simples link **não pode dispensar autenticação** de dados empresariais; convites e senhas devem ser entregues por canal seguro apesar de SMTP desligado. O PC precisa ficar ligado, conectado à Internet e sem suspensão enquanto o cliente usa; queda de energia/conexão tira o link do ar. Não publicar ou expor o PC nesta fase de planejamento.

Documentação dos fornecedores sobre requisitos/limites das opções: [1](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/) (Access e domínio), [2](https://developers.cloudflare.com/tunnel/) (túnel somente com saída do PC), [1](https://tailscale.com/kb/1223/funnel) (Funnel, HTTPS, DNS e limites). Isso **não** substitui avaliação de custo, termos e segurança para a instalação específica.
