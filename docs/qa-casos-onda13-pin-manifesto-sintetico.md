# Fase 2 — Onda 13: PLT-BAK-001 — coadulteração de manifesto e bytes QA

Data: 2026-09-28. Continuação da [Onda 12](qa-casos-onda12-download-arquivo-restaurado.md). **Escopo estritamente QA local:** um documento privado legado de 54 bytes inventados, dois bancos PostgreSQL 17.9 e dois clusters temporários em loopback, diretórios `/tmp` próprios. O ensaio não usa arquivos/URLs de operador, staging compartilhado nem produção. Não foi escolhida política de assinatura, chaves, custódia ou armazenamento; o pin descrito abaixo só existe **na memória do processo que cria o pacote e o restaura nessa mesma execução**. Não é um mecanismo de confiança para backups transportados/armazenados por terceiros.

## Casos rastreáveis

| ID / prioridade | Critério | Evidência observada |
|---|---|---|
| `PLT-BAK-001.P` / P0 | Alterar **juntos** byte do arquivo e seu SHA-256 no manifesto não pode gravar byte alterado no destino quando há hash confiável do manifesto original | **PASSOU no recorte QA:** `QA_RESTORE_INJECT_COTAMPER=1 npm run test:backup-restore:pg:http` (com clientes PG 17.9 QA): DB restaurado no segundo cluster, **497 tabelas**; o helper comparou o SHA-256 dos bytes de `manifest.json` ao pin original **antes** de ler metadados/escrever arquivo; `qa_file_manifest_sha256_mismatch`, **exit 1**, sem `QA_RESTORE_FILE_VERIFIED`, sem HTTP, `QA_RESTORE_TEMP_CLEANED: true`. Teste unitário confirmou ausência do arquivo no destino após a recusa. |
| `PLT-BAK-001.Q` / P0 | Sem pin independente, não dar falsa garantia de autenticidade | **PASSOU enquanto demonstra limitação:** helper QA recusa pin ausente (`qa_file_manifest_pin_required`) sem escrever arquivo. O teste controlado mostrou que, **se** o atacante também fornece um pin recalculado a partir do próprio pacote adulterado, bytes adulterados de mesmo tamanho são aceitos. Assim, SHA-256 **não autentica** pacote não confiável. O pin do runner é origem local em memória, sem persistência/verificação externa; nenhum backup operacional fica aprovado. |
| `PLT-BAK-001.R` / P1 | Manter o restore válido, isolamento HTTP e rejeição de byte alterado sem alterar manifesto | **PASSOU:** após a correção QA, ensaio positivo HTTP completo teve **exit 0**: arquivo 54 bytes/metadata/manifesto, ledger **96/96**, A 200 bytes exatos, B 403, anônimo 401, A revogado 403, auditoria e conta B conferidas, cleanup. Negativo anterior de **um byte sem atualizar manifesto** continua recusado `qa_file_archive_sha256_mismatch`, **exit 1/cleanup**. `npm test` **106/106**, typecheck **exit 0**, build **66/66**, checagens sintáticas e `git diff --check` sem erros. CI remoto/UAT não executados. |
| `PLT-BAK-001.S` / P1 | Injeção negativa não operar sem isolamento | Teste unitário: `QA_RESTORE_INJECT_COTAMPER=1` sem pacote sintético/dois clusters é recusado antes de criar banco (**exit 2**). URLs externas e `CLIENT_DOCS_DIR` continuam recusados pelos guards anteriores. |

**Defeito QA `PLT-DEF-019` (corrigido, retestado):** o runner da Onda 12 comparava `manifest_sha256` com o valor guardado pela origem **após** o helper já ter gravado o arquivo restaurado. Ao coadulterar byte + `sha256` do manifesto, a verificação interna do helper podia aceitar ambos antes de o runner detectar a divergência. Correção limitada ao protótipo QA: `restoreSyntheticFileBundle` agora exige `expectedManifestSha256` de fora do pacote e o compara antes de parse, consulta do DB ou escrita; o runner passa o pin produzido pelo seu próprio `saveSyntheticFileBundle`. Os testes de pin ausente, pin original e pin escolhido pelo atacante evidenciam tanto a proteção limitada quanto a lacuna de confiança. **Não alterar API de produção com base neste protótipo.**

Evidências temporárias fora do Git: `/tmp/qa-wave13-helper.log` (6/6 testes de bundle), `/tmp/qa-wave13-co-tamper.log` (negativo, exit 1 + cleanup), `/tmp/qa-wave13-http-positive.log` (positivo, exit 0 + cleanup), `/tmp/qa-wave13-corrupt-file-regression.log` (negativo legado, exit 1 + cleanup), `/tmp/qa-wave13-tests.log`, `/tmp/qa-wave13-typecheck.log`, `/tmp/qa-wave13-build.log`; build de clientes 17.9 da tag `REL_17_9` só em `/tmp/qa-wave13-pg`, logs `/tmp/qa-wave13-configure.log` e `/tmp/qa-wave13-build-tools.log`. Binários e logs podem não persistir entre sessões. Para reproduzir, obter clientes PostgreSQL 17 **de origem controlada**, não apontar para banco existente: `QA_PG_DUMP_BIN=/caminho/qa/pg_dump QA_PG_RESTORE_BIN=/caminho/qa/pg_restore QA_RESTORE_INJECT_COTAMPER=1 npm run test:backup-restore:pg:http` deve terminar **exit 1**; sem a injeção, **exit 0**. Os clientes temporários compilados são exceção para QA, não empacotamento de produção.

## Decisão e bloqueios

**NO-GO** para backup/restore operacional ou homologação do portal: não existe canal aprovado e independente para pin/autenticação do manifesto, gestão/custódia de chaves, assinatura, criptografia, armazenamento, retenção e recuperação, nem snapshot consistente DB+FS sob concorrência, cobertura de todos os arquivos, PITR, RPO/RTO, CI remoto ou UAT. SHA-256 isolado e pin em memória **não** resolvem confiança em restore posterior. A API administrativa de backup continua fail-closed. Nenhum dos **222 requisitos** existentes foi promovido automaticamente; sem deploy, commit, push ou merge nesta onda. **Próxima etapa depende de decisão humana** sobre política de arquivos, âncora de confiança e responsáveis; aguardar `CONTINUAR` com essas definições ou delimitar expressamente outro recorte QA seguro.
